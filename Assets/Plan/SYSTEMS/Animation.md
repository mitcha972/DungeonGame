# Character models and animation

Assessment and repairs: 2026-11-13. CharacterCombat owns damage/projectile windows, cooldown and action recovery; CharacterAnimator owns clip selection/presentation. Existing locomotion/input/UI ownership remains unchanged. [Combat](Combat.md), [Player](Player.md), [Skills](Skills.md) and [resource gathering](ResourceNodes.md) own their gameplay contracts.

## Verified defects and repairs

- Twelve project-owned standalone clips retained 26 old movement/damage/projectile/AttackHitEvent callbacks. The child enemy Animator has an empty compatibility receiver; forwarding these events would compete with CharacterCombat. Removed only those obsolete callbacks through AnimationUtility; retained footstep/landing events and all clips/GUIDs. See [event changes](../Validation/animation-event-repairs.json). Unity reserialized the edited clips to its current format.
- CharacterAnimator previously used layer 1 for main-hand equipment and layer 2 for offhand equipment, but the player controller defines Override=1, Right Hand=2 and Left Hand=3. Equipment now selects named hand layers, case-insensitively for the enemy controller, and does not disable the attack layer on unequip.
- PlayerCombat resolves its Animator in children, matching CharacterAnimator and supporting child-Animator hierarchies.
- Ability() used the 0.3-second hit-recovery timer for roughly one-second casting clips. The ability recovery timer now uses at least the authored start clip length; controller exit transitions remain authored separately. Hit reaction recovery retains its existing timing. This does not implement a production ability input or complete spell effects.

## Remaining content and integration gaps

The [asset audit](../Validation/animation-audit.json) records controller states, weapon clip arrays, ability data, prefab avatars and event inventory. Paths in the initial audit describe the assessment before folder organization; [move manifest](../Validation/animation-moves.json) maps old paths to current identities.

- PlayerHolder and Enemy_Main have valid humanoid avatars. Visual quality, equipment fitting/clipping and all body variants still need art review; a valid avatar alone does not certify skin weights.
- Spider's gameplay Animator uses Character Animator with a generic spider avatar instead of the available native spider setup/overrides. Its native demo controller contains only Idle. Existing overrides cover some common clips, not a complete independently verified gameplay controller. Needs rig-appropriate locomotion, attack, hit and death wiring plus runtime bone-motion verification.
- Metalon is generic, has two Animators and uses the humanoid character controller. The native Polygonal Metalon/Demo controllers contain many null motions; existing override references also require recovery/validation. Do not substitute humanoid clips onto this rig or claim it fixed by renaming folders.
- Giant has an outer combat Animator and an inner GiantDummy Animator playing its own idle controller. These can compete for the model; select one authoritative Animator and verify binding/retargeting before removing either. Standalone Giant attack/run/walk controllers have null motions in the audit.
- Character Animator has empty BlockStart/BlockIdle/BlockDrop/BlockAttack motions; blocking animation for those enemy variants is unauthored. Player AttackRecoil and AbiltyBost states also have no motion. Keep state names/serialized identities until their callers/content are deliberately migrated.
- Acid, Giant-Stomp, Giant-Swipe and Metalon - Stab weapon definitions have no light/heavy clip arrays. Native enemy presentation is incomplete; do not silently fall back to human punches as an art-complete result. Bow has a light shot but no authored heavy shot.
- Fire Ball and Heal have start clips but no castAnimation. Player input actions contain no ability action and PlayerController does not route one. The independent RPG skills implement XP/books, not ten playable skill animations; the old PlayerSword E poller logs selected legacy passives. Full healing/casting effects, cooldown/resource rules and input design remain prototype work.
- Gathering uses a real collection loop and MiningLoop; chopping shares the mining placeholder. Dedicated chopping, axe/pickaxe/filling visuals and first-person hands/tools remain missing art. Drink/Equip clips existing in a controller do not establish consumable/equip gameplay coverage.
- Roll/dodge clips and states exist, but the current project input map has no roll/dodge action. Treat them as available content, not implemented controls.
