## Mouse-facing third-person camera — implemented 2026-11-15

PlayerHolder/Player_Main now use camera-facing, view-relative movement: mouse yaw turns the upright body (smoothed in third person), W/S move forward/back, and A/D strafe without choosing facing. Vertical look changes camera pitch only. This is the aim-focused strafing pattern illustrated by [Epic's Lyra reference](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine), not a claim that every action RPG uses the same controls or that Fortnite's exact animation system was reproduced.

ThirdPersonController remains the sole movement/facing/view owner. It drives StablePlayerViewTarget, which both configured camera modes follow. Before repair, the motor pitched ThirdPersonCameraTarget while the active PlayerFollowCamera followed the undriven StablePlayerViewTarget (inspected target pitch 15 degrees, actual camera 0). The unused equal-priority ThirdPersonFollowCamera component is now disabled in PlayerHolder. No automatic player toggle, delayed reset or extra camera controller was added. On re-enable the motor reapplies the selected mode/first-person visibility without resetting view angles. Enemy interaction focus no longer overrides body facing; interactions themselves remain intact. SetRotateOnMove remains as a compatibility callback without movement-facing behavior.

Player Animator retains its speed blend and existing action layers, with MoveX/MoveY directional child blends using existing forward/backward/left/right humanoid clips. Side/back clips run at 0.6 rate in the walking blend and normal rate in the running blend. This is basic directional blending, not stride warping or new turn-in-place art.

Changed: ThirdPersonController.cs, Player_Main.prefab, PlayerHolder.prefab and Player Animator.controller; original asset/script GUIDs and hierarchy identities retained. No runtime script was added.
