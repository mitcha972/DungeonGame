# Inventory, equipment and chests

Prefab locations (2026-11-13): ItemInteract pickups remain in `Assets/Prefabs/Items/{Armor,Weapons,Consumables}`; equipped/display mesh prefabs are now in `Assets/Prefabs/Models/Equipment/{Armor,Clothing,Weapons,Consumables}`. Generic Item is in Items/Templates; inventory Canvas/slot templates are in UI/Inventory. These are distinct roles, not duplicates; GUIDs and contents were preserved. See [folder guide and validation](../MAINTENANCE.md#prefab-organization--2026-11-13).

**Implemented prototype.** Files moved to Assets/Scripts/Inventory/{Items,Equipment,UI,Chests}; Interactable/world pickups belong to World/Interactions. [Shops](Shops.md) describe merchant storage. No inventory or purchase algorithm changed in organization.

Inventory.Awake creates null slot entries and derives capacity from configured UI slots. The capacity-with-zero-count audit finding is superseded. Add fills an empty slot and returns failure at capacity; indexed operations guard bounds, refresh UI and notify. ItemInteract destroys pickups only after successful Add. ChestInventorySlot checks source membership and successful destination Add before removal. ScriptableObject item definitions have no quantity/unique-instance/save model.

CharacterEquipment owns slot/equipment/mesh dictionaries and modifiers/notifications. Equipment and bag state now commit together before notifications, guarded against reentrant gear changes. Indexed swaps return replaced gear into the source slot. PlayerEquipment adds UI; EnemyEquipment loads defaults. UnequipAll is a reset operation used by class selection; gameplay U uses UnequipAllToInventory and retains equipment if inventory is full. Preserve these distinct semantics.

Health Consumable validates owner/slot/health, heals through PlayerStats.Heal and removes the consumed entry. Damage modifier behavior is not implemented. Dropping uses an optional Item.worldPrefab pickup, falling back to the existing equipment-mesh path. TryDropItem rejects unsupported items before UISlot removes anything; UISlot also checks exact current slot membership. Items without either representation remain unsupported.

UIPointerEvents supplies native callbacks while retaining vendor presentation compatibility. Slot/index ordering and actual references still matter. Source verifies initialization/transfer/event/consumption paths; [maintenance](../MAINTENANCE.md) lists executed tests. Current full-capacity gear swaps and native hotkeys have the focused coverage below; tooltip/right-click behavior, broader class reset coverage and every prefab variant still need targeted checks. Next design dependencies are identity/quantities/persistence/economy, not another slot initialization rewrite.

Quest turn-ins use generic InventoryItemAmount/Count/CanExchange/TryExchange APIs. Exchange builds a candidate slot list before mutation; reward capacity includes consumed slots. Quest transactions defer inventory notification until state/XP commit. Existing slot storage/equipment behavior is retained; stacks and durable item identity remain unimplemented. See [quests](Quests.md).

Merchant integration (2026-11-13): Inventory owns serialized gold (default 100); ShopInventory uses deferred TryExchange notification to commit stock, gold and bag together. Player bag remains one item per slot. See [shops](Shops.md) for rules and validation.

Resource gathering reuses the atomic exchange API to grant quantity N in N free bag slots; no stacks were added. ItemType.Resource is appended after the existing enum values for Logs/Copper ore. Normal inventory notification updates existing quest possession objectives. See [resource nodes](ResourceNodes.md).

Skillbooks now extend the existing Item.Use path: ten nonstackable definitions grant exactly 100 matching skill XP, validate source slot/owner, consume before XP observers and notify afterward. Failed use retains the book; stale callbacks cannot reuse a consumed entry. Existing one-item-per-slot storage is unchanged. See [Skills](Skills.md).

Consumable now optionally applies a StatusEffectDefinition, reserving its exact slot before application events and restoring on failure. Poison Potion is a separate asset; duplicates retain the item. Health consumables retain their branch. Setup and tests: [status effects](StatusEffects.md).

## Equipment and weapon ownership — 2026-11-15

CharacterEquipment is the single owner of equipped items and instantiated visuals, exposed through read-only Items/Visuals views. Inventory-indexed equip and TryUnequipToInventory commit bag and gear state before events; full bags retain equipment, repeated startup Equip of the same definition is idempotent, and reentrant gear/attack requests during notification are rejected. PlayerEquipment adds slot presentation; EnemyEquipment retains definition-driven startup choices. The formerly empty menu-preview subclass is consolidated into CharacterEquipment; the two unused compatibility shell scripts are removed.

Equipment.weaponAttacks directly references a WeaponAttackSet for each main-hand weapon. Armor/shields have no attack-set requirement. CharacterEquipment.innateAttacks explicitly describes bare-hand/natural attacks when the main-hand slot is empty. No animator-owned category search, available-weapon list or duplicated current-equipment array remains. Existing item categories continue to serve inventory/content classification; they do not choose an attack set.

Replacing/removing a weapon cancels the old execution/motion, detaches the old damage-volume visual and restores authored unarmed collider bounds. Armor hiding is recomputed from all remaining covering pieces, so removing one overlapping piece does not expose another piece's region. Stat modifiers, skeleton references, drops and existing shield behavior retain their owners. Direct startup/class/AI Equip does not consume a bag slot; interactive indexed equip still respects animation busy state.

CharacterEquipment and CharacterAnimation deliberately remain separate: gear transactions/meshes/stats have a different lifecycle from animation playback. CharacterCombat chooses a motion and snapshots its damage, duration/window/interval and projectile values before notifying observers. Animation receives that motion, not the responsibility for selecting weapon rules. See [animation](Animation.md) for authoring and state synchronization.
