# Complete Codebase Audit

Audit date: 2026-11-08
Unity version: 6000.3.28f1
Scope: C# code and code-related package/version declarations only

## 1. Executive summary

This is an established Unity prototype with recognizable building blocks for third-person movement, combat, enemies, equipment, inventory, loot, progression, destructible objects, and procedural dungeon generation. It is not a blank project and does not need a ground-up replacement. The main architectural direction—ScriptableObject definitions, shared character stats/combat, reusable equipment managers, and a common interactable base—is a useful starting point.

The code is not yet a dependable end-to-end RPG loop. The most consequential source-level findings are:

1. The player inventory is created with capacity but no slots; its normal Add path therefore finds no free slot. Several callers also fail to handle a rejected add, including chest looting.
2. The normal (non-ability) projectile path does not initialize projectile damage or range. Ability projectiles do.
3. There are two independent player progression/skill state objects. Enemy XP updates PlayerStats, while the skill-tree bootstrap passes the separate Player object's skills to the UI.
4. Equipment-change notifications are not consistent: the overload used for direct equipment changes invokes callbacks before the new equipment is registered, and invokes two callbacks on replacement.
5. Damage/defence behavior differs across melee, projectile, and blocking paths. Blocking subtracts armor before calling stats, where armor is subtracted again; hit animation is also requested twice on the unblocked combat path.
6. Movement and input code is split across a Starter Assets controller, a custom player controller, older first-person code, and demo controllers. In particular, movement-enable flags are written by the custom controller but never read by the Starter Assets controller.
7. Dungeon-generation retry and start/end selection use unbounded recursion, and room quotas are mutated without being reset on regeneration.

These are source findings, not claims about which components are active in a particular scene. Serialized references, live prefab composition, scene use, and Play Mode behavior were intentionally not examined.

## 3. Architecture and execution map

### Startup and player data

- GameController.cs stores static player name/class/floor/difficulty values and delegates player setup to PlayerContent.
- MenuController.cs selects a Class, updates menu text, and begins the loading-scene flow.
- PlayerContent.cs assigns the name and class to PlayerStats; PlayerStats.Start() initializes health and equips the class equipment.
- Class.cs contains class health and equipment data. The class health field has no consumer in the inspected code; equipment is consumed by PlayerStats.SetUpEquipment().
- Enemy.cs and EnemyStats.cs provide an analogous ScriptableObject-driven enemy stat/equipment/drop path.

This is a serialized-data-led setup, but some values (notably player health) are not consistently propagated from definition assets to runtime stats. Exact serialized configuration remains unverified.

### Player controls and movement

- ThirdPersonController.cs is a Starter Assets-derived CharacterController movement/camera loop. It consumes StarterAssetsInputs.cs, whose input callbacks are compiled only when the Input System and Starter Assets symbols are enabled.
- PlayerController.cs separately reads legacy Input APIs, handles click-to-focus, attack/ability input, dodge animation, and movement-enable callbacks.
- FPC.cs is an older first-person controller path. PlayerMotor.cs is a separate NavMeshAgent-based follow/move path. The demo player has its own movement and mouse-look scripts.
- UICanvasController.cs controls inventory visibility and cursor state. Camera and cursor behavior is also present in Starter Assets input and legacy camera scripts.

Source contains multiple control styles; only scene/prefab inspection can identify the live one and its attached components.

### Combat, damage, and enemy behavior

1. PlayerController calls PlayerCombat.Attack() or Ability().
2. CharacterCombat.Attack() checks animation/cooldown state and raises OnAttack; CharacterAnimator chooses a weapon-associated clip and starts the animation.
3. Melee animation hit windows are exposed through CharacterCombat.EnableDamage() / DisableDamage() to AttackHitBox.cs.
4. Projectile creation is implemented in PlayerCombat.cs and EnemyCombat.cs; collision and range handling are in Projectile.cs.
5. Both hit paths call CharacterCombat.TakeDamage(), which delegates health/armor/death to CharacterStats.cs and animation/knockback/effects to character components.
6. EnemyAi.cs uses a coroutine-driven state machine and NavMeshAgent; it targets the player, patrols, repositions, attacks, searches, and dies.

The shared base classes are valuable, but damage resolution and state transitions are not consistently centralized. Some operations assume required components and target references are present.

### Data-driven architecture and content scaling

The project already has a useful foundation for defining multiple content assets against shared runtime code:

- Content/system: Items | Existing reusable definition: Item.cs ScriptableObject | What can vary as data today: Name, description, item type, icon, price, and a shared Use entry point. | Current limit: No runtime item-instance/quantity/stack model; most behavior is in subclasses or hardcoded branches.
- Content/system: Weapons and armour | Existing reusable definition: Equipment.cs extends Item | What can vary as data today: Slot, mesh, covered mesh regions, armor/damage/range modifiers. A common EquipmentManager attaches meshes and publishes stat changes. | Current limit: EquipmentSlot/ItemType are enums; animation/projectile selection uses a configured WeaponClass list and matching item type. Per-weapon unique behavior is not data-dispatched.
- Content/system: Weapon presentation | Existing reusable definition: WeaponClass.cs | What can vary as data today: Shared light/heavy animation clip sets and projectile prefab per item type. | Current limit: Attack flow, animation state names, and lookup behavior remain hardcoded in CharacterAnimator/CharacterCombat; no data-defined attack pipeline or fallback validation.
- Content/system: Consumables | Existing reusable definition: Consumable.cs | What can vary as data today: Effect amount, StatModifier, and optional particle prefab. | Current limit: The Health case is implemented, Damage is a TODO, and every new effect type needs a code change. Use does not consume an item or clamp healing.
- Content/system: Abilities | Existing reusable definition: Abilities.cs | What can vary as data today: Ability asset can define target, projectile, damage, range, speed, cooldown, and animation/effect fields. | Current limit: Common ability code only plays the start animation and optionally spawns the projectile; several definition fields (target, cooldown, modifier/effect, cast animation) have no implemented consumer.
- Content/system: Enemies | Existing reusable definition: Enemy.cs | What can vary as data today: Base stats, XP, default equipment levels/chances, and loot definitions. EnemyStats and EnemyAi supply common stat and behavior components. | Current limit: Adding stat/gear variants can reuse code; distinct AI/abilities still require code. The AI is one coroutine-heavy, hardcoded state machine.
- Content/system: Classes | Existing reusable definition: Class.cs | What can vary as data today: Class description/icon/health and starting equipment arrays. | Current limit: Class.health is not applied in code; class setup calls the indexed equipment path with slot index 0 for each item.
- Content/system: Loot | Existing reusable definition: Loot.cs and enemy/chest/shop arrays | What can vary as data today: Item/drop prefab and chance can be configured per definition. | Current limit: Separate drop implementations, hardcoded chance rolls, and caller capacity handling; no shared loot service.
- Content/system: Dungeon rooms | Existing reusable definition: DungeonGenerator.Rule in DungeonGenerator.cs | What can vary as data today: Room prefab, coordinate bounds, obligatory flag, type, and mutable count. | Current limit: Grid traversal, start/end selection, retry, and placement policy are fixed in code. Counts mutate across restarts.
- Content/system: Skills | Existing reusable definition: PlayerSkills.cs | What can vary as data today: Enum-based skill identity and prerequisite function. | Current limit: Skill identities/prerequisites, six UI buttons, and selected-skill cases are hardcoded; most unlockable effects are empty or log-only.

In practical terms, many swords or armour pieces can use one Equipment definition shape and one equipment/stat/mesh path; ordinary enemy variants can use Enemy data with the shared AI; and existing consumable types can vary amount and effect visuals. This avoids one gameplay script per asset as long as content stays within the behaviors the shared code actually supports. Content requiring a new damage/effect rule, weapon behavior, enemy decision tree, skill effect, or slot/type needs code work.

The design is partly data-driven rather than fully data-authored. Existing data assets provide configuration, while enums, input bindings, animation-state names, effect switches, stat application, room algorithms, and AI transitions define behavior in C#. The source audit does not inspect or assume how many such assets exist or how they are configured.

### Inventory, items, equipment, and world interactions

- Item.cs, Equipment.cs, Consumable.cs, Abilities.cs, and WeaponClass.cs define data assets and their use behavior.
- Inventory.cs is the player slot store. InventoryUI binds slot components; UISlot, InventorySlot, and HotKeySlot provide use, drag/drop, and hotkey behavior.
- EquipmentManager.cs tracks equipment, stat callbacks, mesh attachments, and item drops. PlayerEquipmentManager adds player equipment UI; EnemyEquipmentManager loads probabilistic enemy defaults.
- Chest and shop code has separate inventory models and UI/slot implementations. World objects derive from Interactable.cs; item pickup, chests, shops, doors, enemies, and dungeon exits specialize it.

The item definitions are reusable, but there is no runtime item-instance/stack model. Inventory and equipment UI operations directly mutate shared lists and rely on matching slot indices.

### Progression, UI, and supporting systems

- LevelSystem/LevelSystemAnimated implement experience/level state; player UI callbacks update bars and labels.
- PlayerSkills and UI_SkillTree implement a skill-point/unlock UI. A separate Player component also owns a level system and skill list in parallel with PlayerStats. PlayerSword currently has empty skill cases or debug-only messages rather than implemented skill effects.
- Tooltip, window, bar, drag/drop, health display, screen damage, camera shake, and animator-event helper scripts provide UI/presentation utilities.
- DestructibleObject uses HealthSystem to spawn break effects and a broken object. Drag-and-drop object grabbing is a separate experimental interaction system.
- Menu/settings/loading/floor-display code is present. PlayerPrefs use found in SlimUI scripts stores settings/preferences; no player progression/inventory/dungeon save contract was found.

## 4. Findings and risks

Confidence refers to the source-level conclusion. Whether a path is active depends on runtime wiring that is outside this audit.

### 4.1 Player inventory has no default slots and failed transfers can lose items

Impact: High — Confidence: High

Inventory.cs initializes items as new List<Item>(20). This sets capacity, not count. The loop in Add() iterates only to items.Count (lines 21–40), so a newly constructed empty list immediately returns false; it does not append an item or create slot placeholders. Remove, Swap, and AddToSlot then index the list and assume those slots exist.

This breaks more than pickup: the indexed equipment path calls inventory.Remove(SlotIndex) when its target equipment slot is empty (EquipmentManager.cs, lines 130–165), which assumes that the list and corresponding UI slot contain that index. PlayerStats.SetUpEquipment() sends every starting class item through Equip(item, 0). With an empty equipment slot, this calls inventory.Remove(0); it can index an empty list or remove an unrelated item at index zero if one is present. ChestInventorySlot.ItemSelect() ignores the Add() result and removes the item from the chest regardless, so a failed player transfer can destroy the last visible reference to the item.

The list is public/serialized, so manually populated slots could mask or change the observed result; no such asset configuration was inspected. The player inventory has no explicit slot-count contract: methods assume items and inventoryUI.slots have matching indexes and lengths.

### 4.2 Normal projectile attacks do not initialize projectile damage/range

Impact: High — Confidence: High

Projectile.cs declares damage and range as private fields, initialized only by StartUp() (line 39). The normal EnableProjectile() paths in PlayerCombat.cs and EnemyCombat.cs set owner/stat references and apply force but do not call StartUp(). The ability overloads do call it. Thus the default projectile damage/range remain zero on the ordinary path. CharacterStats clamps resulting damage to at least one, so ordinary projectiles can still cause a one-point hit rather than using the intended weapon damage; enabled range expiration can also use a zero range.

### 4.3 Progression and skill-tree state are disconnected

Impact: High — Confidence: High

PlayerStats.Awake() constructs one LevelSystem, LevelSystemAnimated, and PlayerSkills (PlayerStats.cs, lines 37–40); enemy deaths award XP to PlayerStats.AddXP() (EnemyStats.cs, line 61). Separately, Player.cs creates its own LevelSystem and PlayerSkills, and Testing.cs supplies player.GetPlayerSkills() to the skill tree. These are different in-memory objects. Therefore enemy XP and the skill points generated by PlayerStats level-ups do not reach the skill list that this skill-tree bootstrap supplies. The Player XP example is commented out.

The XP/stat and skill UI responsibilities need one shared owner or an explicit synchronization path before progression can be treated as an integrated system.

The unlock state also does not yet imply an implemented skill: PlayerSword.cs leaves the Earthshatter/Whirlwind branches empty and only logs for the listed stat skills.

### 4.4 Equipment callbacks are early and can be duplicated

Impact: Medium — Confidence: High

The indexed equip overload calls Unequip(slotIndex, SlotIndex, newItem) and that method invokes onEquipmentChanged before the caller assigns currentEquipment[slotIndex] = newItem (EquipmentManager.cs, lines 81–84 and 160–162). Listeners that query the equipment dictionary during the event see a state without the replacement.

The no-index overload calls Unequip(slotIndex)—which invokes (null, oldItem)—then invokes (newItem, oldItem) again before inserting the new equipment (lines 111–118 and 193–194). CharacterStats.OnEquipmentChanged removes old modifiers for either event; on a replacement through this overload, old modifiers can therefore be removed twice. EnemyEquipmentManager.Setup() uses the no-index overload, so it is not merely an unused API path. Player indexed equipping still has the event-before-state-update issue.

### 4.5 Blocking and hit feedback apply inconsistently

Impact: Medium — Confidence: High

For a blocked melee/projectile hit, AttackHitBox.cs and Projectile.cs subtract the target's armor before forwarding damage. CharacterStats.TakeDamage() always subtracts armor again, including blocked hits. Blocking therefore applies armor mitigation twice, while an unblocked hit applies it once. The result is a different and unintuitive block formula, particularly at high armor.

For unblocked combat hits, CharacterCombat.TakeDamage() calls myStats.TakeDamage(), whose base implementation requests CharacterAnimator.GetHit() (CharacterStats.cs, line 57); CharacterCombat then requests the same hit animation again (line 133). This duplicates hit feedback work.

### 4.6 Death assumes a non-null attacker and, for enemies, a player attacker

Impact: Medium — Confidence: High

The one-argument CharacterStats.TakeDamage(int) calls Die(null) when health reaches zero (CharacterStats.cs, lines 94–109), but base Die() immediately reads attackOwner.name (line 118). PlayerStats.Update() calls that overload for its Y-key damage test (PlayerStats.cs, lines 57–60); if the test kills the player, the null dereference occurs before PlayerStats.Die() can request a reload. EnemyStats.Die() also assumes the attacker has PlayerStats (EnemyStats.cs, line 61). Environmental, neutral, or non-player damage can therefore fail during death/XP handling.

### 4.7 Movement locks do not gate the Starter Assets controller

Impact: Medium — Confidence: High for the code path; active-path status unknown

PlayerController.DisableMovement() writes movementController.canMove and canRotate (PlayerController.cs, lines 328–336). ThirdPersonController declares those fields (line 17), but its Move() and CameraRotation() methods do not read them; the controller continues to process input from its own update loop. Animation callbacks that rely on these flags therefore cannot stop this movement path.

The custom controller also contains empty MouseLocked, MouseUnlocked, and UpdateText methods, and ChangeMouseMode() has no call site in the inspected source. Beyond this specific gating bug, legacy FPC, the NavMeshAgent player motor, and demo movement scripts coexist with the Starter Assets path. The active controller cannot be selected without the prohibited scene/prefab inspection. Input handling is likewise split between Input System callbacks and legacy Input calls; compatibility settings were not inspected.

### 4.8 Dungeon generation has unbounded retry/selection recursion and persistent mutable quotas

Impact: Medium — Confidence: High

DungeonGenerator.cs recursively calls FindStartRoom() when its random search finds no eligible visited cell; FindEndRoom() does the same ([line 102]). Maze generation recursively restarts when fewer than half of the grid cells were visited ([lines 299–304]). None of these retry paths has a maximum attempt count or a configuration guard.

Generation also decrements rooms[randomRoom].numb for each placed room ([line 188]), while ReStart() clears generated children and the board but does not restore those room counts ([lines 57–69]). Repeated floors can consequently run with altered/depleted room quotas. The code has no explicit graph/connectivity validation between generation and room instantiation.

### 4.9 Consumable use and generic item dropping are incomplete

Impact: Medium — Confidence: High

Consumable.Use() applies its effect but does not remove itself from the inventory. UISlot.ItemSelect() delegates to Use() without a general consumption/removal step. Health healing also adds directly to currentHealth without capping it at maxHealth (PlayerStats.cs, lines 108–110); the damage modifier branch remains a TODO.

In the opposite direction, generic UISlot.RemoveFromInventory() sends any Item to EquipmentManager.DropItem(), which casts it to Equipment and immediately reads its equipment fields (EquipmentManager.cs, lines 207–215). Dropping a non-equipment item such as a consumable therefore dereferences a null cast.

### 4.10 Enemy AI has a target null-check after its first dereference

Impact: Medium — Confidence: High

In EnemyAi.Attacking(), the coroutine evaluates target.transform before checking target == null (lines 363–367). If the target disappears between the state transition and coroutine execution, the intended search-state fallback is bypassed by a null reference. The broader AI is coroutine/state coupled: ChangeState() calls StopAllCoroutines() and starts state/update coroutines, which warrants careful transition testing before adding behaviors.

### 4.11 Player class health and several feature fields are not wired through code

Impact: Low to Medium — Confidence: High for source usage

Class.health is declared in Class.cs, but no inspected player setup code assigns it to PlayerStats.maxHealth; PlayerStats.StartUP() only copies the already-existing maxHealth to currentHealth. Likewise, some declared ability behavior fields (target, modifier/stat modifier, cooldown, particle effect) are not consumed by the common CharacterCombat.Ability() flow. The consumable damage effect is explicitly unimplemented.

These may be supplied or bypassed by serialized configuration, but the code does not currently establish them as working gameplay behavior.

### Inventory and equipment call-path verification

The following traces cover active source references to the player inventory APIs and both specialized chest/shop inventory APIs. Calls that occur only in comments are identified as inactive; third-party collection operations unrelated to these inventory types are excluded.

- API / path: Inventory.Add(Item) | Active callers and observed behavior: ItemInteract.OnInteract() checks the returned bool before destroying the world pickup. ChestInventorySlot.ItemSelect() and ShopInventorySlot.UseItem() ignore the result. EquipmentSlotUI.ItemSelect() ignores the result when transferring an equipped item back to the player inventory. | Success/capacity/index assumptions: The pickup caller handles failure; all three UI transfer callers behave as if it succeeded. Chest slot clears and removes its source item even on failure. Shop slot neither removes stock nor charges currency, so it is not a completed purchase flow. Equipment transfer can lose the unequipped item if player inventory rejects it.

- API / path: Inventory.Swap(Item, int) | Active callers and observed behavior: EquipmentManager.Unequip(slot, index, item) returns the old equipment to the equipment item's source inventory index when replacing an occupied equipment slot. | Success/capacity/index assumptions: No success result or bounds check; assumes list and UI slot have the index. Class setup assumes one fixed source index for all items and the equipment manager assumes the source slot is valid.
- API / path: No-index Equip(item) | Active callers and observed behavior: EnemyEquipmentManager.Setup() equips selected defaults through this overload. PlayerEquipmentManager's override wraps the overload and can also return early when animation is busy. | Success/capacity/index assumptions: No inventory slot is consumed by this overload. It has no result for the caller to distinguish a completed equip from the player override's busy-animation early return.
- API / path: Indexed and no-index Unequip() | Active callers and observed behavior: EquipmentSlotUI.ItemSelect() calls no-index Unequip(equipmentSlot) and ignores the returned oldItem, then tries to add its own item to inventory without checking success. EquipmentManager.UnequipAll() is called by the U-key branch in the same manager's Update() and removes equipment without transferring it to inventory. | Success/capacity/index assumptions: No-index unequip invokes the callback even if the slot was already empty and does not add the removed equipment to inventory. UI transfer assumes successful add; UnequipAll is a destructive clear from inventory's perspective unless a separate drop/save path exists.
- API / path: ChestInventory.Add/Remove(Item) | Active callers and observed behavior: ChestScript.Start() rolls loot and calls Add; ChestInventorySlot.ItemSelect() calls Remove after attempting a player transfer. | Success/capacity/index assumptions: space defaults to 4, Add returns false at capacity, and ChestScript ignores it. The chest slot removes/clears the chest item regardless of player Inventory.Add success; Remove itself ignores the underlying List.Remove result.
- API / path: ShopInventory.Add/Remove(Item) | Active callers and observed behavior: ShopScript.Start() rolls stock and calls Add; the only shop Remove call found in ShopInventorySlot is commented out. | Success/capacity/index assumptions: space defaults to 4, Add returns false at capacity, and the script ignores it. Shop stock remains after click; transfer failure is ignored and no price/currency path is implemented.
- API / path: UI population and slot counts | Active callers and observed behavior: InventoryUI.Start() discovers child InventorySlots; ChestScript.Interact() and ShopScript.Interact() loop to inventory.items.Count and index UI slot arrays at the same index. | Success/capacity/index assumptions: The player inventory has no explicit slot count and does not validate item-list length against UI slots. Chest/shop inventories cap at four by default, but if their configured space or loot exceeds the actual slot-array length, population indexes beyond the UI array. Neither list capacity nor slot counts were checked in serialized assets.

This confirms the player, chest, shop, and equipment flows are separate inventories with implicit index coupling; it does not establish which UI objects are active or how their arrays are configured.

### Test strategy for audited high-impact findings

These are recommended regression tests for a later implementation stage, not tests run during this code-only audit. Any runtime wiring and serialized fixture required by a test must first be verified by the Unity Agent.

- Finding: 4.1 Player inventory initialization and transfers | Test scenario: Start with a new inventory; test add at empty/full capacity, remove/swap at valid and invalid indexes, pickup success/failure, chest transfer into a full inventory, and class setup with multiple starting items. | Successful behavior: The selected capacity contract is explicit; operations do not throw or silently lose/overwrite items; rejected transfers retain the item at the source; class setup equips every intended item exactly once without removing an unrelated index.
- Finding: 4.2 Normal projectile initialization | Test scenario: Fire ordinary player and enemy weapon projectiles and ability projectiles with known damage/range; test both collision and range expiration. | Successful behavior: All paths use the configured damage and range, with consistent owner attribution; range expiry is based on the configured value and no ordinary projectile silently falls back to minimum damage.
- Finding: 4.3 Progression/skill-tree ownership | Test scenario: Award enemy XP, trigger a level-up, then open the skill UI through the actual bootstrap and unlock a skill; also verify skill effects. | Successful behavior: The UI reads the same live progression/skill state that receives XP and skill points; unlock availability and points update once; selected skills invoke the intended effect rather than an empty branch.
- Finding: 4.4 Equipment callbacks | Test scenario: Equip into empty and occupied slots through both overloads; observe equipment dictionary and stat/animator listeners during callbacks; repeat with enemy setup. | Successful behavior: Equipment state is already consistent when a single change notification is delivered; modifiers are removed/applied exactly once; mesh and UI correspond to the final equipment.
- Finding: 4.5 Damage, blocking, and hit feedback | Test scenario: Compare same incoming damage/armor with and without block, including high armor; count hit animation/effect invocations for melee and projectile. | Successful behavior: A single documented mitigation formula applies; block effect is intentional and not accidental double armor; each accepted hit produces one hit-feedback sequence.

- Finding: 4.9 Consumable use and dropping | Test scenario: Use health consumable at low/full health and multiple times; use/drop a non-equipment item; test equipment drop. | Successful behavior: Consumable effect respects max health and the chosen consumption/stack policy; an unsupported effect is rejected explicitly; item dropping handles equipment and non-equipment types without null casts or loss.
- Finding: 4.10 Enemy AI target race | Test scenario: Remove/disable/destroy the target between state transition and attack coroutine execution; test each state transition while disabled/dead. | Successful behavior: AI detects invalid targets before dereference, transitions to a defined search/idle state, and does not leak or restart conflicting coroutines.
- Finding: 4.11 Class/ability data wiring | Test scenario: Configure a class health value and ability target/cooldown/modifier/effect fields distinctly from defaults; create and use the player/ability from the runtime path. | Successful behavior: Runtime stats and ability behavior reflect the authored values, or unsupported fields are removed/clearly rejected instead of appearing configurable but having no effect.
